# Android Change Review

对当前改动做证据驱动的 Android 代码审查。只关注本次 diff 引入或放大的问题，不把项目既有设计意图误判为缺陷。

全程在当前对话内完成，禁止启动 Subagent / Task。

## 判定依据

拿不准某个写法是否有问题时，读对应知识库核对，不要凭记忆下判断。按需读一篇，不整包拉：

- 测量布局、动画、约束链、列表复用、触摸分发、insets → `android-view-wiki`
- 分层归属、`ViewModel` 边界、`UiState` 与状态收集、一次性事件、Repository 与单一可信来源 → `android-architecture-wiki`
- 权限、前台服务与后台限制、intent 与组件导出、targetSdk 相关的行为差异 → `android-sdk-behavior-wiki`
- 协程与 `Flow` 的语义、Kotlin 惯用写法与陷阱 → `kotlin-wiki`

这些知识库给的是判定依据，不是问题清单——仍然只报本次 diff 引入或放大的问题。

## 审查流程

1. 明确范围
   - 运行 `git status --short` 和 `git diff HEAD` 获取本次全部改动（含 staged）。
   - 只审本次改动文件；按需读取直接调用方、被调用方和相关接口。
   - 先理解原有不变量、降级策略和改动目标，再判断对错。
   - 不处理无关改动。

2. 检查正确性
   - 正常路径是否实现目标。
   - null、空集合、异常、失败重试、网络中断、进程重启等边界。
   - 新旧状态切换是否连续，降级与恢复路径是否正确。
   - 回调顺序、回调重入、重复调用、幂等性和漏回调。
   - 缓存、磁盘、内存和服务端状态是否一致。

3. 检查 Android 风险
   - 生命周期销毁后是否仍更新 UI 或持有 Context/View。
   - 主线程是否执行网络、数据库、大 JSON、递归文件或重 IO。
   - 协程/Rx/线程切换是否正确，任务是否可取消。
   - 共享状态的复合操作是否原子，是否存在竞态、越界或可见性问题。
   - 文件下载、校验、解压、标记、读取、删除的发布顺序是否安全。
   - 快速点击、并发请求、重复下载时行为是否稳定。

4. 检查工程约束
   - 先读取并遵循项目规则；若项目采用 `app → feature → data → core → SDK` 分层，确保依赖只能向下。
   - 修改保持周边代码风格，没有引入不必要架构或依赖。
   - diff 是完成目标所需的最小改动。
   - 不把已有且明确的产品/架构设计当作本次问题；必要时列为“上下文”，不要标 P0/P1/P2。

5. 验证
   - 重新完整阅读 `git diff HEAD`，确认没有残留调试代码、冲突标记和多余空白。
   - Android 项目默认不编译；仅在用户明确要求时执行编译或测试。
   - 不能验证的部分明确写入“验证缺口”，不要假装已验证。

## 严重级别

- **P0**：确定导致严重崩溃、数据丢失、安全事故或大面积不可用，必须立即修复。
- **P1**：现实路径可触发的功能错误、生命周期问题、竞态、错误缓存或明显回归，合入前修复。
- **P2**：低概率边界、可维护性问题或非阻断优化，可后续处理。

每条问题必须包含：

1. `文件:行号`
2. 具体触发顺序或输入条件
3. 用户可见影响
4. 最小修复建议

没有完整触发链和代码证据时，不输出问题。

## 修改权限

- 若这是实现任务结束前的自审：直接修复 P0/P1，重新检查最终 diff 后再汇报。
- 若用户只要求审查或审计：只报告问题，不修改代码，除非用户明确授权修复。
- P2 默认不顺手修改。

## 输出格式

```markdown
结论：通过 / 有阻断问题

P0
- 无 / [文件:行号] 问题、触发条件、影响、最小修复

P1
- 无 / ...

P2
- 无 / ...

验证
- 已执行：<实际执行的命令或检查>
- 未执行：<跳过的验证及原因>
- 验证缺口：<无法验证的部分>
```

有问题时按 P0 → P1 → P2 排序；没有问题时明确写“未发现由本次 diff 引入的 P0/P1/P2”，同时说明剩余验证缺口。
