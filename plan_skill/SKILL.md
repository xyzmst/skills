# 开工前的计划

`post-change-gpt-review` 定了**什么时候**要计划（B/C 档）和决策表要答什么（关系、归属、单一来源）。这里定**计划长什么样**、**怎么知道它够了**、**改完拿什么对账**。

计划的价值不在文档本身，在于**方向错的时候改的只是几行文字**。C 档还多一层：落成文件才有后面拿 diff 对账的可能，留在对话里改完就无从核对。

    10|## 位置：项目自己的 `docs/plan/`，独立小仓库

放 `docs/plan/<日期>-<一句话>.md`。`docs/` 常被主仓库 `.gitignore` 忽略（yidui.android_opt 是这样）——直接放主仓库跟踪不到的目录里等于没有版本历史，和聊天记录一样脆。做法是在 `docs/plan/` 单独 `git init` 一个本地小仓库：

```bash
mkdir -p docs/plan && cd docs/plan && git init -q
```

`.gitignore` 忽略的是 `docs` 这个路径本身，git 不会遍历被忽略目录，所以这个嵌套仓库对主仓库完全透明——不会有 submodule/gitlink 警告，也不会把 AI 计划提交混进业务代码历史。首次建仓时确认：

```bash
cd <项目根> && git status --short docs/    # 应该什么都不输出
```

主仓库已有对应需求文档（如 `docs/通话场景优化.md`）就在 `plan/` 里另起文件、正文互相链接，不合并进旧文档——旧文档没有版本历史，`plan.md` 需要。

两条对账线不要混：**代码 diff** 走主仓库 `git diff`（改的文件是不是计划里那几个）；**计划本身的修订史**走 `docs/plan/` 自己的 `git log`/`git diff`（谁改的、批准前后差异）。

## 四栏，缺一栏不算计划

```markdown
# Plan: <一句话>（<日期>）

## 改哪些文件
<路径>（新建 / 修改，各自为什么是这个文件）

    20|## 顺序
1. ...    ← 顺序就是风险排序，最险的排第一步先撞

## 风险与归属决策
按最没把握排最前。每条：我选了 A，因为…；不确定的是…；备选是 B。
备选给到具体结构（用哪个机制、状态放进什么类型、View 进哪个容器），让人能直接答「按 A 来」。

## Proof
每条需求点 → 拿什么证明它对。
```

    30|## Proof 不是「功能出来了」

Proof 分双轨，根据改动类型选：

- **UI / 布局改动 → 状态组合矩阵。** 把本次触碰的每个可见/不可见、每个内容长度档、每个音/视频态各列一维，标出哪几格会争同一块空间——那几格就是必验的。单态验过不等于验过，重叠只在组合态暴露。
- **业务 / 协议 / 状态机改动 → 状态转移矩阵。** 列出 `当前状态 × 触发事件（IM/按钮/超时/退出） → 下一状态 + 副作用（停流/取消Timer/释放资源）`。死锁、内存泄漏和重复回调只在异常退出和交叉时序暴露。

测试套件跑不起来、又按规则不跑编译验证时，Proof 落在两处，两处都要写：

- **静态能确认的**——约束链挂没挂上、`when` 覆盖 sealed/enum 有没有漏分支、改了签名的调用点全不全。写清查哪个文件的哪一行，改完真去查。
- **只有运行时能证的**——真机时序、并发交错、服务端行为。写进「验证缺口」，明说要人在真机上看哪几格，不靠推理下结论。

    40|## 质询三问（自己答，不等用户问）

交计划前逐条答完，答案并进「风险与归属决策」：

1. **这个改动可能破坏什么**——沿数据流从产生走到消费一遍，含没改的部分。
2. **哪一步风险最高**——它该被排到第一步。
3. **我选择不做的其他方案是什么，为什么不做。**

第三问最值钱。归属类决策（View 挂哪层、状态归哪一层、常量住哪）在需求和设计稿里永远沉默，不主动把被丢弃的选项摆出来，它就不会被任何人看见——直到它变成 bug。只报结论不报备选等于自我合理化。

    50|## 终止判据

不是「我看着行」，是：**一个没看过这段对话的人，能不能只凭这份计划做出这个改动。**

这条判据的作用是把「我懂了」和「它写清楚了」分开。很多计划看着没问题，只是因为缺的那部分正好在我脑子里自动补上了。

## 审批界面：canvas 是渲染，不是产物

计划看不下去等于没有计划。涉及 UI 或决策表有并列备选时，把它渲染成 canvas 让人批（读 `canvas` skill）。

**唯一真相源是仓里的计划文件。** canvas 只能放在 `~/.cursor/projects/<workspace>/canvases/`，不在 git 仓库里，拿不到 diff 对账，不算产物。它是一次性的：批完就不管，计划改了**整个重新生成，不要手改 canvas**。不维护就没有漂移——反向同步一次就变成两个真相源。

只画渲染真能加价值的四样，**每样都带判据，不满足就不画**——出图也是成本，图多了和计划长一样会没人看。四样各答一个问题、互不替代，同时满足两条就出两张。

四样里只有**改动类图走 PlantUML 出 PNG**，`.puml` 源码跟计划文件一起进仓——它是意图的记录，批完不该丢。另三样走 canvas。**两者拼不到一页，别试**：canvas 只能 import `cursor/canvas`，没有图片组件也不能 `fetch`，嵌不了 PNG；反过来让 canvas 自己画类图要手写 SVG（`computeDAGLayout` 只给坐标，且节点尺寸是全局固定值，撑不开按成员数变高的类框），二三百行 TSX 换 PlantUML 二十行文本，而且渲染结果我看不到，改错了只能靠人反馈。

- **状态组合矩阵**——本次触碰的状态不止一维时画：每个可见/不可见、每个内容长度档、每个音/视频态各列一维，标出哪几格会争同一块空间。单一状态没有组合可列，不画。
- **约束拓扑**——这次的 View 要挤进一条已有约束链、或落进一个已有元素在争的槽位时画，`layout-chain.py --json --id <view>` 直接喂，别手抄（手抄过一次，行号两个都错了）。自成一体的新布局不画：列表 item、独立弹窗不和既有元素争位置，图上只有它自己，没有既有链可对照。
- **改动类图**——判据就是分档判据本身：**这次改动会不会产生一个「这东西住在哪、和谁什么关系」的答案**。会就画，**不看改动量**（`PayModule.currentWaitDeadline` 只动一个类一个成员，正是最该画的），**也不看有没有新增**（把方法从 Activity 下沉到 ViewModel 一个成员都没多，但它是纯粹的归属改变，最该画）。**判不准就画**：漏画的代价是归属错误进了代码，多画只是多渲染一次。
  画法：PlantUML，`~/.agents/skills/plantuml-wiki/scripts/puml-render.sh <in.puml>` 本地渲染成 PNG（源码不外传，别走 plantuml.com）。颜色照业界 diff 惯例：`<color:green>` 新增、`<color:blue>` 原地改（改签名 / 改类型 / 重命名）、`<color:red>--删掉的成员--</color>` 删除或移出（creole 删除线）。无标记的是列出来作对照的既有成员——没有对照，自检里「新加的字段/参数，已有的能不能覆盖」就答不了；无关成员用 `.. 其余成员省略 ..` 折叠（原生分隔符）。
  **新增的状态往更公共的位置放时（`object` / 单例 / 基类 / core 层），既有读取方一个都不许省**，跨模块的尤其要画：四条箭头从四个不同 package 汇聚到同一个字段，「正确性靠什么维持」当场就有答案。只画新增点和一条写入线，图上一个类一条边，看着完全无害——`PayModule.currentWaitDeadline` 就是这么过去的。读取方靠侦察阶段 `grep` 拿，本来就该查。
  **成员按 Kotlin 原样写全**：`+ fun normalizeTimeout(sec: Int?): Long`、`- private var waitTimeoutMs: Long`，参数类型、可空 `?`、返回类型、`val`/`var`、默认值一个都不能省——半截签名答不了「改了签名的函数调用点全改了吗」和「参数默认值和兜底函数是不是在表达同一个意图」。`+ - #` 就是 UML 可见性，正常用。「为什么」写成**行尾注释，跟成员同一行**——PlantUML 按有没有括号分属性区和方法区，注释单独一行会被拆到另一个区去。
  **性质必须标**，它就是生命周期：`interface`/`abstract`/`enum` 用关键字，单例用 `class PayModule <<object>>`——`object` 是进程级、`ViewModel` 随页面销毁，而归属决策问的正是「这个状态该活多久」。**层用 `package "feature 层" { }` 包起来**：连线跨层往上（`data` 指向 `feature`）就是违反铁律，分了层一眼可见，不分就看不出来。整类增删用背景色（`class OldHelper #Pink`；类名不能包 `<color>`，会报语法错）。**关系的增删要标在线本身上**：`-[#green]->` 新增、`-[#red,dashed]->` 摘掉或违规——只写 label 不够，**两条样式相同的反向边会被合并成一条**，违反铁律的反向依赖正是这么在图上消失的，线型一变就分开画了。**有方向的改动两端都要画**：成员移动，源头红色删除线加 `// 移至 X`、落点绿色加 `// 移自 X`；换父类换接口，旧关系红虚线、新关系绿实线——归属改变有方向，只标一端看不出它从哪来、又从谁身上摘掉的。
  固定头、图例位置、成员分区、颜色和线的语法读 `plantuml-wiki`（`references/class.md` 和 `style.md`，每条都实测过），图糊了读它的 `layout.md`。
  **渲染完自己看一眼 PNG 再交出去。** 注释被拆进属性区、两条同样式的反向边被合并成一条，这两类错 PlantUML 照样退出 0、照样出图，只有看图才发现。
  两种不画：**归属和关系现成的**——往既有扩展点填东西（列表加一个 item 类型、实现一个已有接口、sealed class 加一个子类型）、只改方法体、纯透传地多加一个参数，框架早定好了谁住哪；**纯数据结构**——字段跟 API 响应一一对应的 bean，字段是服务端定的不是设计选择，画出来等于抄一遍接口文档。
- **决策表**——归属决策有两个都说得通的备选时画：每条备选一张卡，A/B 具体结构并排，点一下选。选择落进 `.canvas.data.json`，等于批准被记录下来。

类图画的是**意图**，约束拓扑画的是**现状**，这决定了数据从哪来：意图在动手前必然已经知道，不解析代码、也不配提取脚本（解析出来的是现状，可能读错；意图不会错，错了就是方案错，恰好是这一步要拦的）。唯一要查现状的是上面那条既有读取方，但那是侦察的产出，不是给图配的提取器。约束拓扑的现状必须由脚本出，不能靠目测 XML。

C4 那条广为流传的告诫「不要手画代码级图，IDE 能生成、代码一改就过期」针对的是**文档化现状**，对意图图不成立：要画的代码还不存在，IDE 生成不出来；图批完就扔，没有过期窗口。反过来也成立——哪天想用它记录现状，这条告诫就该听，那种图该由 IDE 出。

「改哪些文件」「工作顺序」是纯列表，canvas 画它纯属浪费，留在 markdown 里。改动类图不属于这一类：它有层级（类 → 成员）和对照（既有 vs 新增），文件路径列表两者都没有，答不了「在哪个类里加什么」和「是不是加多了」。

## 批准之后

- **先把批准结果写回计划文件，再动代码。** 每条归属决策下补一行：`批准：A（<日期>）；未采用 B，因为<一句话>`。canvas 的 `.canvas.data.json` 在仓库外，不写回去这件事就只活在聊天记录里——半年后翻代码问「当初为什么住这儿」，答案得在仓里。被否掉的备选也要留着，那是这条决策唯一的对照。
- 实施偏离计划 → 在同一次提交里改计划，别让它腐烂成一份没人信的旧文档。
- 改完先按 Proof 逐条过，再拿 diff 对计划：**动的文件是不是那几个**。多出来的每个文件说清为什么——这是范围悄悄扩大的最早信号。
    60|- 计划里写的验证缺口，汇报时原样带出去，不要因为「看起来没问题」就吞掉。
