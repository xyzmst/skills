# 评估：证明 skill 真的有价值

写完一个 skill，在一个 prompt 上试了下，看着能用。但它在各种措辞下都稳定吗？边界情况呢？**比不装 skill 强吗？**结构化评估回答这些问题。

这一套比较重。默认不跑；拿不准某个 skill 值不值、或者两个写法说不清哪个好时才跑。

## 核心手法：带 / 不带对比

**每个用例跑两遍：一遍带 skill，一遍不带。**不带的那遍是基线。没有基线就无法判断收益来自 skill 还是模型本来就会。

改进已有 skill 时，基线换成**改动前的快照**：改之前 `cp -r` 出来一份，基线指向快照，输出存 `old_skill/` 而不是 `without_skill/`。

**每次运行必须是干净上下文**，不能带上一次运行或开发 skill 过程中的残留状态——否则测的不是 `SKILL.md` 本身。有 subagent 的环境天然隔离（每个子任务全新开始），没有就一个运行开一个 session。

## 测试用例

三部分：**prompt**（真实用户会打的话）+ **expected_output**（人类可读的成功描述）+ 可选的**输入文件**。存在 skill 目录下的 `evals/evals.json`：

```json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "月度销售数据在 data/sales_2025.csv，找出收入最高的 3 个月做个柱状图",
      "expected_output": "一张展示收入 Top 3 月份的柱状图，轴有标签、有数值",
      "files": ["evals/files/sales_2025.csv"]
    }
  ]
}
```

- **起步只写 2~3 条。**在看到第一轮结果之前不要过度投入，之后再扩
- 变化措辞、详略和正式度：有的口语（"帮我把这个 csv 清一下"），有的精确（"解析 data/input.csv，丢掉 B 列为空的行，结果写到 data/output.csv"）
- 至少一条覆盖边界：畸形输入、异常请求、或 skill 指令可能有歧义的情况
- 带真实语境：路径、列名、个人背景。"处理一下这个数据"测不出任何东西
- **先不要定通过标准**，只写 prompt 和期望输出。断言等看过第一轮产出再加

## 工作区结构

每一轮完整评估占一个 `iteration-N/` 目录：

```
csv-analyzer/
├── SKILL.md
└── evals/evals.json          # 只有这个是手写的
csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/      # 产出的文件
    │   │   ├── timing.json   # token 数与耗时
    │   │   └── grading.json  # 断言结果
    │   └── without_skill/
    │       └── ...
    └── benchmark.json        # 聚合统计
```

`timing.json` 记 `total_tokens` 和 `duration_ms`。在 Claude Code 里 subagent 完成通知会带这两个值，**要立刻存下来，别处不留存**。

## 断言

**在看过第一轮输出之后再写。**你通常不知道"好"长什么样，直到 skill 真跑过一次。

| 好断言 | 为什么 |
|---|---|
| `输出文件是合法 JSON` | 可程序化验证 |
| `柱状图的两个轴都有标签` | 具体、可观察 |
| `报告里至少有 3 条建议` | 可计数 |

| 坏断言 | 为什么 |
|---|---|
| `输出质量好` | 太虚，无法评分 |
| `必须出现 "Total Revenue: $X" 这个短语` | 太脆，换个措辞的正确输出会被误判失败 |

**不是所有东西都要断言。**文风、视觉设计、"感觉对不对"这类难以拆成通过/失败的质量，交给人工评审。断言只留给能客观检查的东西。

## 评分

对每条断言评 PASS / FAIL 并**记具体证据**。证据要引用或指向实际输出，不能只是给个意见。

```json
{
  "assertion_results": [
    { "text": "输出包含柱状图文件", "passed": true,
      "evidence": "outputs 目录下找到 chart.png (45KB)" },
    { "text": "两个轴都有标签", "passed": false,
      "evidence": "Y 轴标了 'Revenue ($)'，X 轴无标签" }
  ],
  "summary": { "passed": 3, "failed": 1, "total": 4, "pass_rate": 0.75 }
}
```

两条原则：

- **PASS 必须有具体证据，不给疑罪从无。**断言要求"包含摘要"，而输出只有个"Summary"标题加一句含糊的话 → **FAIL**：标签在，实质不在
- **评分时同时审断言本身。**注意哪些太易（不管 skill 好坏都过）、太难（输出明明不错也过不了）、或无法仅从输出验证，下一轮修掉

机械检查（合法 JSON、行数对不对、文件存在且尺寸符合）**用脚本**，比 LLM 判断可靠且能跨轮复用；其余交 LLM 评。

比较两个版本时用**盲测**：把两份输出交给 LLM 裁判，**不告诉它哪份来自哪个版本**，让它按自己的 rubric 给整体质量打分（组织、格式、可用性、完成度）。这能补断言的盲区——两份输出可能都过了全部断言，但整体质量差很多。

## 聚合与 delta

每种配置算通过率 / 耗时 / token 的均值和标准差，存 `benchmark.json`：

```json
{
  "run_summary": {
    "with_skill":    { "pass_rate": {"mean": 0.83}, "tokens": {"mean": 3800} },
    "without_skill": { "pass_rate": {"mean": 0.33}, "tokens": {"mean": 2100} },
    "delta": { "pass_rate": 0.50, "time_seconds": 13.0, "tokens": 1700 }
  }
}
```

**delta 才是决策依据**：skill 花了多少（时间、token）买到了多少（通过率）。

- 多 13 秒、换通过率 +50 个百分点 → 值
- token 翻倍、换 +2 个百分点 → 不值

stddev 只在每个用例跑多次时才有意义。早期只有 2~3 个用例、每个跑一次时，看原始通过数和 delta 就够。

## 模式分析（聚合数字会藏掉重要信息）

算完 benchmark 之后逐条看：

- **两种配置下都必过的断言 → 删掉或替换。**模型不带 skill 也能做到，它们只是在虚高带 skill 的通过率，不反映真实价值
- **两种配置下都必败的断言 → 查原因。**要么断言坏了（要求模型做不到的事），要么用例太难，要么断言在查错的东西。下一轮之前修掉
- **带 skill 过、不带 skill 败的断言 → 这才是 skill 真正的价值所在。**搞清是哪条指令或哪个脚本起了作用
- **同一用例时过时不过（stddev 高）→ 收紧指令。**要么 eval 本身 flaky（对模型随机性敏感），要么 skill 的指令有歧义、模型每次理解不同。加例子或更具体的指导
- **查时间和 token 的异常值。**某个用例慢 3 倍，去读它的执行 trace 找瓶颈

## 人工评审

断言只能查你想到要查的东西。人能抓到你没预料的问题、技术上正确但没抓住重点的输出、以及难以表达成通过/失败的毛病。

反馈要**可执行**：

```json
{
  "eval-top-months-chart": "图缺轴标签，且月份按字母序而非时间序排列",
  "eval-clean-missing-emails": ""
}
```

"图缺轴标签"可执行，"看起来不好"不可执行。**空反馈代表这条过了评审**，迭代时只关注有具体抱怨的用例。

## 迭代

三份信号，各自指向不同的问题：

| 信号 | 指向 |
|---|---|
| 失败断言 | 具体缺口：漏了某一步、指令不清、某种情况没处理 |
| 人工反馈 | 更广的质量问题：方向错了、结构差、技术正确但没用 |
| 执行 trace | **为什么**出错：指令被忽略说明有歧义，浪费步骤说明该简化或删除 |

把三份信号连同当前 `SKILL.md` 一起交给模型提改法——它能把失败断言、评审抱怨和 trace 行为里的共同模式串起来，这件事手工做很费劲。提改法时要加的四条要求见 authoring.md 的「迭代时的四条要求」。

循环：提改法 → 审阅并应用 → 在新的 `iteration-<N+1>/` 里重跑全部用例 → 评分聚合 → 人工评审 → 重复。

停的条件：满意了、反馈持续为空、或轮次之间不再有明显改进。

## 症状 → 排查

| 症状 | 排查 |
|---|---|
| 不知道 skill 到底有没有用 | 「核心手法」——必须有不带 skill 的基线，否则没有参照 |
| 通过率看着高但感觉没变强 | 「模式分析」第 1 条：两种配置都必过的断言在虚高数字 |
| 不知道该断言什么 | 先跑一轮再写断言，见「断言」开头 |
| 断言总过但输出其实很水 | PASS 给得太松，见「评分」；或者断言太易 |
| 断言总不过但输出看着没问题 | 断言太脆或在查错的东西 |
| 同一用例时过时不过 | 指令有歧义或 eval flaky，见「模式分析」第 4 条 |
| 两个版本都过了全部断言，说不清哪个好 | 用盲测，见「评分」末段 |
| skill 有效但明显变慢变贵 | 看 delta，算清花了多少买了多少 |
| 加规则通过率不再升 | 过度约束，见 authoring.md「迭代时的四条要求」末段——删指令试试 |
| 某个用例耗时异常 | 读它的执行 trace 找瓶颈 |
