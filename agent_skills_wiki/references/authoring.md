# 正文：素材、密度、规定程度

## 素材从哪来

**最大的坑：让模型凭通用训练知识生成 skill。**产出的会是"妥善处理错误""遵循认证最佳实践"这类空话，而不是具体的 API 模式、边界情况和项目约定。这类 skill 占着上下文却不改变任何行为。

有价值的 skill 只有两个来源。

### 一、从真实任务里抽

先和 agent 一起完整做完一个任务，过程中正常给上下文、做纠正、表达偏好，然后把可复用的模式提炼出来。重点记四样东西：

- **走通的步骤序列**
- **你中途做的纠正**——"用 X 不用 Y"、"先检查边界 Z"。这是最高价值的部分，因为它精确标出了 agent 默认会走错的地方
- **输入 / 输出的实际格式**
- **你提供的项目专属事实**：约定、约束、agent 不可能自己知道的背景

### 二、从已有产物合成

有成体系的现成知识时，喂给模型让它合成。关键是**项目专属材料**，不是通用文章——用团队真实的故障报告和 runbook 合成的数据管线 skill，一定强于用一篇"数据工程最佳实践"合成的，因为前者带着你的 schema、失败模式和恢复流程。

好素材：

- 内部文档、runbook、风格指南
- API spec、schema、配置文件
- **code review 评论和 issue**——暴露反复出现的关注点和评审者的期望
- **版本控制历史，特别是修复补丁**——改动本身就暴露了真实模式
- 真实故障案例及其解决过程

## 初稿一定要改

第一版基本都需要打磨。拿真实任务跑，然后把结果——**全部结果，不只是失败的**——喂回去。问三件事：什么造成了误触发、漏了什么、能砍掉什么。

哪怕只做一轮"执行 → 修订"，质量都明显提升；复杂域通常要几轮。

**读执行 trace，不只看最终输出。**agent 在无用步骤上浪费时间时，常见原因有三个，对应三种不同的修法：

| trace 里看到的 | 原因 | 修法 |
|---|---|---|
| 试了好几种做法才走通 | 指令太模糊 | 给具体命令或明确默认值 |
| 做了和当前任务无关的动作 | 指令不适用但它照做了 | 加触发条件，或删掉该指令 |
| 在选方案上反复 | 给了太多选项没有默认值 | 见「给默认值不给菜单」 |

## 密度：只补 agent 缺的

skill 一旦激活，`SKILL.md` 全文就和对话历史、系统上下文、其他激活的 skill 一起挤在同一个上下文窗口里，**每个 token 都在和其他内容抢注意力**。

判据只有一句：**「没有这条指令，agent 会做错吗？」答否就删。**不确定就去测。

不用写：PDF 是什么、HTTP 怎么工作、什么叫数据库迁移。要写：项目约定、领域流程、非显然的边界、该用哪个具体工具或 API。

```markdown
<!-- ❌ 啰嗦，agent 早就知道 PDF 是什么 -->
## 提取 PDF 文本
PDF（便携式文档格式）是一种常见文件格式，包含文本、图片等内容。
要提取文本需要用库，推荐 pdfplumber，因为它能处理大多数情况。

<!-- ✅ 直接给 agent 不知道的部分 -->
## 提取 PDF 文本
用 pdfplumber。扫描件退回 pdf2image + pytesseract。
```

**如果不带 skill agent 就已经能把整个任务做好，这个 skill 可能压根不该存在。**

## 范围：像设计函数一样划

skill 要封装一个**内聚的工作单元**，并且能和别的 skill 组合。

- **太窄**：一个任务要同时加载多个 skill，有额外开销和指令冲突风险
- **太宽**：难以精准激活

"查数据库 + 格式化结果"可以算一个内聚单元；再把"数据库运维"也塞进来就是想做太多事了。

## 详尽程度：中等

**过度详尽反而有害。**agent 难以从长文里抽出相关部分，还会被不适用于当前任务的指令带去走弯路。简洁的分步指导 + 一个能跑的例子，通常胜过穷尽式文档。

发现自己在覆盖每一个边界情况时，先想想：大部分是不是该交给 agent 自己判断。

## 规定程度要匹配任务脆弱程度

不是每一部分都需要同样的强制力度。**同一个 skill 里各部分分别校准。**

**给自由**——多种做法都成立、任务能容忍变化时。这种地方**解释 why 比下死命令更有效**：理解了目的的 agent 能做出更好的情境判断。

```markdown
## Code review 流程
1. 检查所有数据库查询有没有 SQL 注入（用参数化查询）
2. 确认每个端点都有鉴权检查
3. 找并发路径里的竞态
4. 确认错误信息没泄露内部细节
```

**写死**——操作脆弱、要求一致、或必须按特定顺序时。

```markdown
## 数据库迁移
严格执行这个序列：
    python scripts/migrate.py --verify --backup
不要改命令，也不要加额外 flag。
```

### 给默认值，不给菜单

多个工具或做法都可行时，**定一个默认 + 简短提一句替代**，不要并列成等价选项。

```markdown
<!-- ❌ 选项太多，agent 会在选择上浪费 turn -->
可以用 pypdf、pdfplumber、PyMuPDF 或 pdf2image……

<!-- ✅ 明确默认 + 逃生出口 -->
用 pdfplumber 提取文本。扫描件需要 OCR 时改用 pdf2image + pytesseract。
```

### 写方法，不写答案

skill 要教 agent **怎么应对一类问题**，不是**对某个具体实例产出什么**。

```markdown
<!-- ❌ 具体答案，只对这一个任务有用 -->
把 orders 表 join 到 customers 的 customer_id，筛 region = 'EMEA'，sum amount 列。

<!-- ✅ 可复用方法，对任何分析查询都成立 -->
1. 读 references/schema.yaml 找相关表
2. 按 `_id` 外键约定 join
3. 把用户请求里的筛选条件变成 WHERE
4. 按需聚合数值列，输出成 markdown 表
```

这不意味着 skill 不能含具体细节——输出格式模板、"绝不输出 PII"这类约束、特定工具的用法都有价值。要点是**方法本身要能泛化，即使个别细节很具体**。

## 什么时候拆 references/

正文超 500 行 / 5000 token 就拆，把详细参考材料移进 `references/` 之类的目录，正文只留每次运行都需要的核心指令。

**拆分的关键不是拆，是告诉 agent 什么时候加载哪个文件。**

```markdown
<!-- ❌ agent 不知道何时该读，通常就不读了 -->
细节见 references/。

<!-- ✅ 带触发条件 -->
API 返回非 200 状态码时，读 references/api-errors.md。
```

一个例外要记住：**Gotchas 不能挪进 `references/`**。原因见 patterns.md——agent 认不出该加载它的时机。

## 迭代时的四条要求

把评估信号交给模型提改法时（信号怎么收集见 evaluation.md），明确要求它：

- **从反馈泛化**：skill 要面对很多不同的 prompt，不只是测试用例。修法要处理底层问题，不要为具体样例打窄补丁
- **保持精简**：少而好的指令常胜过穷尽规则。trace 里显示有无用功（多余校验、不必要的中间产物）就把那些指令删掉
- **解释 why**：「做 X，因为 Y 常导致 Z」比「ALWAYS do X, NEVER do Y」更容易被稳定遵守
- **重复工作打包成脚本**：见 patterns.md 的「打包脚本」

**如果加了规则通过率反而平台化，可能是过度约束了——试着删指令，看结果会不会持平甚至变好。**不确定某条该不该留时，先删掉跑一遍比先加上去更容易看出它有没有用。

## 症状 → 排查

| 症状 | 排查 |
|---|---|
| 写出来全是"妥善处理错误"这类空话 | 见「素材从哪来」——凭通用知识生成的必然如此，要换素材来源 |
| 不确定某段该不该留 | 「没有它 agent 会做错吗」，答否就删；拿不准就先删掉跑一遍 |
| skill 装了但好像没让结果变好 | 可能压根不该存在，见「密度」末段；怎么证明见 evaluation.md |
| agent 试好几种做法才走通 | 指令太模糊，见「初稿一定要改」的表格 |
| agent 做了和任务无关的动作 | 指令不适用但它照做了，加触发条件或删掉 |
| agent 在方案选择上反复 | 见「给默认值，不给菜单」 |
| 一个任务要同时加载好几个 skill | 范围切太碎，见「范围」 |
| skill 覆盖很全但 agent 抓不住重点 | 过度详尽，见「详尽程度」 |
| 指令被忽略 | 通常是有歧义；另见「规定程度」——脆弱操作要写死，其余讲清 why |
| 加了规则通过率不升 | 过度约束，删指令而不是再加 |
| 正文超 500 行 | 见「什么时候拆 references/」，拆完必须写触发条件 |
