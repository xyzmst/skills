# retros — AI 协作失败案例集

**这里不是 skill。**没有 `SKILL.md`，不参与 agent 路由，agent 不会主动读。它是给人看的证据库，用来回答一个问题：**这次的坑该改规则、该改流程，还是就是个例。**

## 为什么需要它

`post-change-gpt-review.mdc` 里卡了一条触发线：同一类问题被抓**第二次**才补进清单，只出现一次先当个例修掉——因为单次样本写进规则容易过拟合出一条边界模糊的新规则，反而增加下次自检的噪音。

这条触发线要能执行，前提是记得住第一次。凭记忆判断"这是不是第二次"必然失败，所以第一次就得留档。**案例集的唯一职责是给"是不是第二次"提供证据。**

## 收什么

只收**agent 判断错了、且错在方案层**的案例。判据：

- 收：结构/归属选错、方案方向错、问题域没被识别（"没人知道它存在"那类）
- 收：同一类错误的第二个实例——哪怕很小，它才是写规则的凭证
- 不收：实现细节写错、拼写、API 记错——那是改一行的事，不构成模式
- 不收：需求变更导致的返工，那不是判断失误

## 案例格式

固定六段，写不满就说明还不够成为案例：

1. **现象**——一句话说清最终暴露成什么样
2. **时间线**——在哪一步本该被拦住、实际在哪一步被发现
3. **根因**——把这次的错抽象成一句可复用的话，不停留在"View 放错了"
4. **为什么没被拦住**——自检清单为什么检不到它，这段最有价值
5. **落了什么**——改了哪个规则文件的哪一段，或明确记「只当个例，没落规则」
6. **待观察**——下次命中同类场景时回来补一行：规则真的拦住了没有

## 怎么用

- 复盘一个新问题时，先扫索引：同类是不是已经有过一次？是 → 达到写规则的门槛；不是 → 记下来，先当个例修掉
- 改规则前先看对应案例的第 4 段，规则要瞄准"为什么没被拦住"，不是瞄准现象
- 隔一段时间回来看"待观察"和"谁发现的"两列，判断该继续改规则还是改流程
