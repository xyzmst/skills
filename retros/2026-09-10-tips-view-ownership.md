# tips View 的槽位归属

- 日期：2026-09-10
- 项目：yidui.android_opt，1v1 恋爱通话场景优化（8.6.600）
- 错误模式：**归属由复用决定，不由约束决定**
- 谁发现的：用户，在代码落地并经过三轮增量改动之后
- 状态：观察中

## 1. 现象

余额不足公屏（付费方）和「对方玫瑰不足」预警标签（收益方）两个贴底左下角的 tips，第一版放在 `fragment_base_live_love_video.xml`（音/视频公共层）。上线后与既有元素重叠：视频态压价格条，音频态挤房间公告。处理重叠时只能反复调 `marginBottom`，怎么调都对不齐；最后把两个 View 挪进 `fragment_love_video_stage.xml` 和 `view_love_video_bottom.xml`（音视频各存一份，Base 层用三个抽象属性取 view），视频态才真正解决。

## 2. 时间线

| 步骤 | 实际发生 | 本该发生 |
|---|---|---|
| 方案 | 未提出"View 挂哪一层"这个问题 | 一次 `grep`：稿子上相邻的价格条 / 公告在哪个布局文件 |
| 落地 | 放公共层，理由是渲染逻辑音视频共用 | 答案是两个不同布局 → 结论自动是各放一份 |
| 自检 | 检查了 z 序（礼物层能不能盖住），判定层级已考虑 | 还该问"谁挤谁"，占位是另一个问题 |
| 后续三轮 | 在既有落点上做增量，落点本身不再被审视 | — |
| 处理重叠 | 连调 margin，每次都"好一点"，未回头质疑方案 | 改的是间距而不是约束，就该回退方案 |
| 最终 | 用户提出该挪进各自布局 | — |

信息在方案阶段是充分的：Figma 稿标明了位置，相邻元素的宿主布局在仓里可查。**不是信息不足，是没做那一步。**

## 3. 根因

把「逻辑要共用」当成了「View 也该住公共层」。这两件事正交：

- tips 与价格条 / 公告真正共享的是**同一个 `ConstraintLayout` 的约束求解器**——这是不可跨容器的资源
- 放公共层后，两者不在同一个容器内，互相挂不上约束，位置只能写死 `90dp`
- 而价格条 / 公告的高度是内容驱动的（公屏双态、标签两行、公告长度不定），固定 dp 永不对齐

一般化：**归属由约束决定，不由复用决定。** 复用需求靠"逻辑上移、位置下沉"解决（抽象属性 / 接口 / `include` / 参数传入）——最终的收尾恰好是这个形状，只是撞出来的，不是选出来的。

## 4. 为什么没被拦住

**a. 把"层级"只理解成 z 序。** 当时确实想过层级，XML 注释还留着「放在礼物层之前，礼物面板弹出时盖在它上面」。正因为想过一遍，产生了"层级已考虑"的错觉。层级是两个独立问题：谁盖谁（z 序，跨布局也能靠 XML 顺序 / elevation 解决）和谁挤谁（占位，只能靠同容器内的约束链解决）。只答了前者就收工。**那条注释本身就是自我合理化的证据。**

**b. 从相邻代码继承了结构决策。** 公共层里已有 `resume_call_tip` / `wait_state_tip`，放那儿是对的——它们全屏居中，不与任何元素争空间、不参与约束链。新 tips 贴底左下角，是另一类东西，但"照着隔壁放"了。这正是 `CLAUDE.md` 明写禁止的那条，而当时的判断依据恰恰是"旁边就这么写"。

**c. 现有架构规则覆盖不到这一层。** 架构铁律管依赖**方向**（app → feature → data → core）和**模块粒度**归属（页面放哪、ViewModel 放哪）。这次一条都没违反：base Fragment 的布局里放 View 完全合法。盲区在**宿主粒度**——同模块内该住公共基类还是子类、进程级单例还是会话对象，此前没有任何判据，只能凭"哪个更通用"，而这个直觉永远指向更公共的位置。

**d. 只验证了单一状态。** 验的是"标签出来了、文案对、秒数在走"。重叠只在组合态暴露：公屏与公告同时在、标签折两行、价格条恰好有内容。没列组合矩阵，这些状态一次都没同时构造出来。

**e. 后续三轮为什么也没发现。** 第一版落地后"View 放哪"变成既定事实，每轮 diff 的审视范围里没有"落点对不对"。且重叠出现时最小改动看起来就是调 margin，每次调完确实好一点，形成正反馈。`android-view.mdc` 里"同一个显示问题修了两次还不对就回退方案"没被触发，因为每次都不是"还不对"而是"好了一些"——**这条规则的触发词应该是「改的是间距而不是约束」，不是「还不对」。**

## 5. 同型复发（写规则的凭证）

同一个需求里已经出现第二个实例，形态完全不同，这才让它够格进规则而不是过拟合单个样本：

`PayModule.currentWaitDeadline`——因为"多个支付入口都要读这个值"就放进程级字段，而它真正的归属是"一次充值会话"。放错之后正确性只能靠"所有入口都记得走 `buyRose`"这个约定维持，于是 `MiApi` 首充弹窗、`TVPlayFragment`、`ExchangeTicketFragment` 全部读到 1v1 上一次的残留值。已记在项目 `docs/通话场景优化.md` 第八条「待修」。

两个实例共有的形状：**放到更公共的位置之后，正确性靠约定维持**（写死一个数 / 记得走某个入口），而不是靠结构保证。

## 6. 落了什么

`cursor_rules/post-change-gpt-review.mdc`，四轮共五处：

| 位置 | 加了什么 |
|---|---|
| 新增「先分档」 | A/B/C 三档，判据是"这次改动会不会产生一个『这东西住在哪』的答案"，会就至少 B 档 |
| 「动手前先说清」入口 | B/C 档先交侦察地形和决策表，**批准前不动文件** |
| 「动手前先说清」bullet | 归属由约束决定不由复用决定；往更公共位置放之前答"正确性靠什么维持"，答案是约定就是放错了（带本案例与 `currentWaitDeadline` 两个反例） |
| 「动手前先说清」节末 | 决策按最没把握排最前，每条带不确定点和备选；只报结论等于自我合理化 |
| 「Subagent 默认不开」 | 归属类决策有两个都说得通的备选、定不下来 → 开 `design-review`；理由写明自审在这类问题上最不可靠 |

`android_view_wiki/references/constraintlayout.md`：补一条症状行（跨布局的两个 View 挂不上约束 → 只能靠写死 dp）。

**没落进规则的**：架构铁律那段判据要手动贴进 Cursor 设置的 User Rules（不是磁盘文件，agent 改不了）。

## 7. 外部依据

调研自 AI 内参，两篇：

- [造软件工厂：slop 不是模型问题，是验证卡在人眼上](https://ai.candobear.com/neican/articles/3cd679b1-08ff-8121-9be1-c81d0606c1d3)——「长运行真正失败的地方不是败在难题上，是败在没人知道存在的问题上」，正是本案例的诊断：问题域从未被提出，所以自检再认真也检不到。对策是先侦察后规划，产出"渲染好的选项和决策表让人去反应"；以及决策账本——让 agent 交出规格沉默处的每个决定，按最不自信排前。**View 挂哪一层正是规格永远沉默的地方**：需求、设计稿、验收标准都不会写它。另有一条硬规则：审计者必须与实现者分离，因为模型审自己的作品"会被自己的意图预先启动，然后合理化"。
- [Anthropic 官方 AI Native 开发手册中译](https://ai.candobear.com/neican/articles/3c9679b1-08ff-8183-a101-dfa9096885c8)——plan mode 的价值在于"设计审查发生在任何代码生成之前，改方向还只是改文档的事"，计划的验收标准是"没看过这段对话的工程师也能只凭它完成改动"。另一条对本项目是**结构缺口**：手册要求"始终给 agent 一种验证自己工作的方式，会话自己检查自己的工作、自己修正错误，然后工程师才看到"，而本项目按用户规则不跑编译验证、无可用测试套件、UI 只有真机能看——**别人可以靠事后测试兜住方案错误，这里只能靠事前决策不错**，这是"侦察 + 决策表"在本项目不是可选优化而是唯一质量来源的原因。
