# 不受约束的中间产物必然被偏离

- 日期：2026-09-22
- 项目：yidui.android_opt，1v1 通话猜拳 / 真心话（`feature` 新玩法）
- 错误模式：**审批载体不受机器约束 → 方案层结论在实现阶段被静默偏离**
- 谁发现的：用户，在实现完成并返工数轮之后
- 状态：观察中

## 1. 现象

plan 阶段做得不算少：需求文档、10 个阻塞项（X1–X10）逐条向用户确认、PlantUML 改动类图、两版交互 canvas。用户对这一段的评价是「plan 阶段大致没问题」。

进入实现后方案层的结论基本没有兑现：

- **架构**：plan 里写明「Repository 只调接口、IM Repository 只监听解析、ViewModel 才写状态机」，实际写出来是多余的 `DataSource` 层 + IM 逻辑混进 API Repository + ViewModel 过重。用户连续三轮要求收敛（「这么简单的东西就不需要 DataSource 了」「怎么 IM 的逻辑也放到这里了」「VM 的逻辑还是感觉有点多」）。
- **UI**：有截图和 Figma 链接，仍然出现自创布局和 shape 填空，用户原话是「你个傻逼，仔细对照设计图」。
- **状态机**：上线前后陆续暴露四个洞——第一轮结束后新邀请切不过来、发起方卡在「等待对方确认 0s」、一直点换题会重置倒计时、倒计时到 0 文案不切换。
- **接口**：整个实现过程中没有先定义任何接口，直接从方法体开始编。用户最后单独提了一句：「我还有个问题，这次实现没有先定义接口，直接编的代码」。

收尾时改用「状态 × 事件」矩阵反向填一遍已实现的 ViewModel，**当场又撞出 5 个此前所有环节都没抓到的缺陷格**（见第 5 段）。

## 2. 时间线

| 步骤 | 实际发生 | 本该发生 |
|---|---|---|
| 需求闭合 | X1–X10 逐条确认，覆盖产品规则与并发语义 | 同时枚举「状态 × 事件」网格，确认规格沉默处 |
| 方案 | 出 plan + 类图 + 交互 canvas，都是 markdown / 图 | 先提交 `interface` + 空实现（`TODO()`）拿批准 |
| 实现 | 入口 + IM + 动画 + 结果页一次铺开 | 按片交付，片内跑偏先收回 |
| 架构偏离 | 文档写的分层与代码不一致，无任何信号 | 偏离签名就会产生签名 diff，review 可见 |
| 自检 | 逐条对需求点、查冗余、查常识错误 | 需求点里本来就没有「QuestionShown 收到 start_invite 怎么办」 |
| 返工 | 用户逐个指出后修 | — |
| 事后补接口 | 我先写下「禁止为形式新增 `ILoveRoomGameRepository`」，被用户纠正 | 先 `grep` 仓内 `I*Repository` 命名约定 |
| 矩阵反填 | 108 格填完，撞出 5 个缺陷 | 这一步本该在写代码之前做 |

信息在方案阶段是充分的：phase 枚举、IM action、两个倒计时、接口失败分支全都已经定下来了。**不是信息不足，是没有一个强制把它们两两相乘的载体。**

## 3. 根因

**审批载体决定偏离概率。** markdown 里的方法签名、UML 类图、状态流程图都不受任何机器约束——编译器不认，完备性不检。实现阶段偏离它们没有代价，也不留痕迹。

受约束的中间产物才有拦截力，这次验证了两种：

- **仓里可编译的 `interface` + 空实现**：批准的是编译器认的东西，之后任何偏离都表现为签名 diff，在 review 里藏不住。
- **行 × 列强制枚举的矩阵**：状态图只画你想到的转移，没想到的在图上根本不存在，所以图看起来永远完备；矩阵是笛卡尔积展开，没想到的格子会留白，空格自己跳出来。

一般化：**能被偏离而不留痕迹的中间产物，等于没有约束力；把它换成一种偏离会报错或留白的形式，才算真的批准过。**

## 4. 为什么没被拦住

**a. UML 制造了「已设计」的错觉。** 类图表达的是类与成员的归属，不表达「事件穿过哪个方法、写进哪个状态」——而这次全部缺陷都在后一个维度上。画了图、图也没错，于是产生了「结构我想过」的判断。这与 tips 案例里「XML 注释写着已考虑层级」完全同型：**产出物本身成了自我合理化的证据。** 用户对 UML 的怀疑是对的（「画什么类图 UML 似乎用处没那么大，特别是复杂的需求」），但原因不是 UML 画得不好，是它答的不是这次要问的问题。

**b. 流程图的完备性是假的。** 两版交互 canvas 画的都是主线：入口 → 邀请 → 接受 → 猜拳 → 出题 → 确认。9 个 phase × 12 个事件 = 108 种组合从未被枚举过。5 个缺陷格因此躲过了 plan、类图、交互图、X1–X10 逐条确认，以及实现后的多轮自检——**每一环都在看同一条主线。**

**c. 契约写在文档里，实现时无成本偏离。** plan 写了职责边界，代码里照样把 IM 解析塞进 API Repository。文档和代码之间没有任何强制关系：不报错、不产生 diff 信号、不影响运行。等到用户读代码时才发现，已经是几百行之后。

**d. 自检清单检不到「格子没想过」。** 自检问的是「需求点逐条对到代码了吗」，而需求点里本来就不包含「`QuestionShown` 收到 `start_invite` 该怎么办」。**规格沉默处的组合态不在任何需求清单里**，逐条对账必然漏掉。这是 tips 案例第 4 段 d（只验证单一状态）在状态机维度上的复现：那次漏的是 UI 组合态，这次漏的是事件 × 状态组合态。

**e. 分档定了但没执行。** 这是教科书式的 C 档（跨模块 + IM 协议 + 状态机），而实际是一次铺开。分片交付没有发生，所以架构跑偏在片内没有机会被收回，只能等整个功能写完由用户整体退回。

## 5. 矩阵的第一份产出（新流程有效性的证据）

反向填 108 格撞出的 5 个缺陷格，全部是实现后多轮自检没抓到的：

| 格子 | 缺陷 | 处理 |
|---|---|---|
| `Asking × 接口失败` | 确认失败后 `questionDeadline` 未清零，`tick` 每秒无限重试确认接口 | 已修 |
| `Asking × 题目倒计时到 0` | 题目为空时自动确认空转，每秒一次，赢家卡在 0s 无题目 | 已修 |
| `Playing × IM 题目` | 动画未播完收到题目 IM 被丢弃，此后永久停在「等待对方确认题目」 | 未修 |
| `Playing × 动画结束` | `result != "win"` 一律当输，平局或漏字段会让双方同时进等待态互相等 | 待服务端确认平局是否可能 |
| `WaitingQuestion × IM 邀请` | 对方另起一局的邀请被丢弃，本侧再也收不到题目，只能挂断 | 未修 |

一个值得记下的观察：**两个已修缺陷共享同一个根因**（`questionDeadline` 是一次性触发器但从未被消费），而它们在矩阵上是两个不相邻的格子，分属「计时」和「接口」两列。按功能点走查不会把这两处联系起来——把它们并列摆在同一张表上，根因才浮出来。这是矩阵相对于逐条走查的额外收益，不只是查漏。

## 6. 同型复发（本次会话内的第二个实例）

形态不同但同族：**用「有几个实现」代替「有没有真实替换点」当作抽接口的判据，且下判断前没查仓内约定。**

我在 plan 里写下「只有一个实现、没有替换或隔离需求时，直接用具体 Repository，禁止为了形式新增 `ILoveRoomGameRepository`」，被用户直接纠正。查了才发现仓内早有既定约定：`IAuthRepository + AuthRepository`、`IMomentRepository + MomentRepository`，Koin 按接口注册。

这和 tips 案例第 4 段 b（从相邻代码继承结构决策）互为镜像：那次是照抄隔壁，这次是凭通用原则下禁令，**两次都跳过了同一步——先查仓内锚点**。「仓内锚点先于范例」这条门槛已经写在 `CLAUDE.md` 第 1 条，说明写下规则和执行规则之间还有距离；这次没加新规则，因为要加的那条已经在了。

补一句判据本身的结论，它比命名更值得记：**接口的存在理由是有第二个实现要被替换，不是「这是一层架构」。** 构造注入进 ViewModel 的 Repository 该抽（测试塞假实现就能跑整台状态机）；ViewModel 不该抽（`ViewModelProvider` 按具体类当 key 取实例并反射构造，接口进不了任何依赖声明，连「只许调契约方法」都约束不了，那该靠 `private`/`internal`）。

## 7. 落了什么

`CLAUDE.md` Hard Gates：

| 位置 | 加了什么 |
|---|---|
| gate 6 | 两次批准：先批准归属、状态模型、规格矩阵和文件白名单；再提交受编译器约束的真实源码骨架，批准类型与签名后才填方法体 |
| gate 6 | 抽接口判据改为「有没有真实替换点」+ 仓内 `I` 前缀命名 + ViewModel 不抽；替换掉原来那条错的「不等于给单一实现机械增加 Kotlin `interface`」 |
| gate 5 | 每片开工前列出该片允许改动的文件，改完 `git diff --stat` 对账，清单外文件出现即违约 |

`plan_skill`（`change-plan`）：

- 「两次批准」：第一次批准设计，第二次批准真实源码骨架；骨架不限于 `interface`，具体 ViewModel / IM Repository 直接提交具体类签名
- 「审批界面」：按问题选择角色故事板、状态矩阵、泳道/事件轨迹、设计稿对照或方案对比；复杂需求最多一个主视图 + 一个完整性视图 + 一个高风险视图
- UML 从 Plan 流程移除：类职责由 Kotlin 骨架表达，行为完整性由矩阵表达，跨端时序由故事板/泳道表达
- 「批准之后」节：白名单**按片给、不按整个需求给**；对账命令写成 `git diff --stat`

新增产出物类型：**状态转移矩阵**（行 = phase、列 = 事件、格 = 下一状态 + 副作用；空格即洞，「不可能发生 / 忽略」也算内容但必须写理由）。本次以 canvas 形式实现，可逐格标注并持久化。

**明确不落的**：用户提议 plan 出完后让 AI 自答「实现逻辑是否合理 / 是否过于复杂 / 是否足够简洁」「是否需要考虑扩展」。这两问没有加，理由是不可反驳——刚设计完方案的 AI 必然答「合理、简洁」，等于再生产一份自我合理化。替代为可数版本：新增了几个类 / 几个 Flow / 几个状态字段、每个新增封装有几个调用点（只有一个就内联）、同一个值有几个写入点。「是否需要考虑扩展」尤其危险，它是在邀请过度设计，正确问法是反向的——**有没有第二个已知调用方**，想象出来的不算。

## 8. 待观察

下次 C 档改动回来补：

- 有没有真的先提交真实源码骨架拿第二次批准，而不是又交一份 markdown 签名
- 状态类需求有没有在写代码前把矩阵列满，空缺数是多少
- 索引「谁发现的」那一列有没有从「用户」变成「矩阵」或「自检」
- **矩阵自己会不会退化成凭证**——这是这次落点最需要警惕的失败模式，与第 4 段 a 的 UML 完全同型：填满 108 格之后同样会产生「我想过了」的错觉。判别方法是看空格和「忽略」格有没有写理由，以及缺陷格是不是集中在少数几列（集中说明真在想，均匀分布往往说明在批量填字）

## 9. 遗留（未修）

- 矩阵找出的 3 个缺陷格未修：`Playing × IM 题目`、`WaitingQuestion × IM 邀请`（客户端可修）、`Playing × 动画结束` 的平局分支（需服务端先确认 `result` 是否会下发平局，协议里也没有作废本局的 action，客户端不该自己造本地超时）
- 8 个待确认格未验：其中 `InviteReceived × 邀请倒计时到 0` 在接受请求失败后会静默把用户踢回入口，`InviteWaiting × 接口失败` 会强制关闭面板，两者都只能真机验
- `CLAUDE.md` 被 `.gitignore:19` 忽略，本身没有版本历史——最重要的约束文件改坏了无法回退
- 仓内一条可机检约束都没有（无 detekt / ktlint / Konsist / `lint.xml` / pre-commit hook），「Fragment 不许 import Repository」这类规则全靠人看。用户本轮选择只改规则、不加构建约束，**所以本案例落的全部是流程约束，没有一条能在违规落地时自动挡住**

## 10. 外部依据

沿用 README 里已引的两篇 AI 内参，这次对应上的是同两条：

- 「长运行真正失败的地方不是败在难题上，是败在没人知道存在的问题上」——这次是 108 格里没人点过的那几格，和 tips 案例的诊断一字不差，只是维度从 View 归属换成了事件 × 状态。
- plan mode 的价值在于「设计审查发生在任何代码生成之前，改方向还只是改文档的事」——本案例补了一个限定条件：**前提是那份文档有约束力**。不受约束的文档只是把返工从代码阶段推迟到代码阶段，没有省下任何东西。

用户在讨论中另提到内参的 Planner vs Traveler 与 Thicker UI 两个概念（未记 URL），方向一致：把判断前移到有渲染结果、有强制枚举的产物上，而不是靠事后走查。
