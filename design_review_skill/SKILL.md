# 设计质量 Review

**这是兜底路径，不是常规流程。** 大部分冗余是可数的事实（同一个函数在一条链上调了几次、默认值和兜底函数是否同义），按 `post-change-gpt-review` 的自检清单数出来就行，不需要外包。

只有真正说不清的设计选择才起——比如这层抽象值不值得、两种写法哪个更适合这个模块。有客观答案的（调用点、作用域、类型、空安全、计数得出的重复）自己查完再来。

## 输入：文件列表 + 真实 diff

**给触碰文件列表，让它自己跑限定 diff。禁止用「我记得改了什么」的摘要替代 diff。**

摘要是实现者的叙述，不是事实：行号会记错，漏改和误改的文件根本不会出现在清单里，reviewer 永远看不到。给文件列表则两头都占——它不用探索改了哪里，拿到的仍是真实改动，限定文件也不会被截断。

## 模型：跟当前会话不同的

`Task` + `generalPurpose`，`run_in_background: true`。

model 选一个**与当前会话不同**的强模型（`claude-sonnet-5-thinking-high` / `gpt-5.6-sol-high` / `gemini-3.1-pro`）。同模型同上下文再想一遍价值很弱；跨家族盲区重叠最小。当前会话就是候选模型之一时，换另一个。

## prompt

```
Full Repository Path: <绝对路径>
改动目标：<一句话>
本次触碰的文件：
<file1>
<file2>
先跑 git diff HEAD -- <上面这些文件> 拿真实改动，可疑处再读周边代码。
主审冗余、过度设计、不必要的抽象/字段/参数、更简洁的等价写法、超出最小改动的部分；顺手发现的明显正确性问题也报。
判据：最小改动（只改需求必要的）、YAGNI（不猜未来用途）、跟随本文件及相邻代码既有风格，不是通用最佳实践。
只报有具体触发条件或明确更简写法的；不报风格偏好，不建议加抽象层/防御代码/测试；代码站得住就直接说没问题。
会破坏行为/正确性的才算 Important，其余算 nit；nit 最多报 3 条，多出的只汇总成一句「另有 N 条风格类」，不逐条列。
每条一行：文件:行号 + 问题 + 改法。只报不改。
```

不传我的取舍、不传为什么这样写合理、不传这几轮踩过的坑——那是要它推翻的东西，喂进去它就顺着认同了。

**判据要放进 prompt，不能假设它自己加载了项目规则。** 实测过：Subagent 起手直接 `git diff`/`grep`，没有任何引用 `CLAUDE.md`/项目规则的痕迹——它大概率在用通用工程判断审我们的代码，不知道这个仓库的具体规范。所以模板最后一行要带上「最小改动、YAGNI、跟随本文件既有风格」，别指望它自己知道。

**必须给「可以说没问题」的许可。** 被要求找问题的 reviewer 即使代码没问题也会硬报几条，追着每条改就变成过度设计。实测过：加了这句许可后，同一份代码、同一个模型，上一轮力主的那条 P0 自己撤了。

## 后台交付分两段

后台跑不阻塞，但第一段汇报**不能给「已完成」的印象**：说清改动内容 + 「设计审查在跑」。结论回来后：

- 有影响正确性或改动目标的条目 → 追一段，说清哪些改了、哪些没改和为什么。
- 零 finding → 不再开口，别用「审过了没问题」占注意力。

要一次交付完整结论就别用后台，同步等。两者不能兼得。

## 拿到结论后

我修，不重复审一遍，不复述它的过程。合理的直接改；不认同的说明理由，不闷着不改。

它缺上下文，会误判：见过它把白名单的放行值当成「无人使用的死常量」（只搜了谁产生这个值，没看消费点）。甄别是我的活，不是照单执行。
